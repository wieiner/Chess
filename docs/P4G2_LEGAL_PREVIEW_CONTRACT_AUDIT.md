# P4G2 Legal Preview Contract Audit

Date: 2026-06-27

Scope: P4G2 Phase 02. This audit defines the smallest safe online contract for server-authoritative legal action preview. It does not change Chess3D rules, native ABI, room semantics, auth, persistence, or the five existing Chess3D RuleProfiles.

## Baseline

The online client can already:

- connect to the public HTTP 80 diagnostic server;
- create two temporary users;
- join matchmaking;
- start an Asgard table;
- request an authoritative snapshot;
- display a board slice from `OnlineSnapshot.SaveGameJson`;
- select From/To cells and submit a `NormalMove`;
- refresh board state from server callback/snapshot after accepted actions.

The main playability gap is that the online UI does not yet ask the server for legal targets after selecting a source cell. The user can click From/To, but the UI cannot distinguish legal target, capture target, wrong actor, stale state, or profile-specific action before submitting.

## Existing Local Preview API

The native Chess3D engine already exposes append-only legal preview ABI:

- `Chess3D_BuildLegalActionPreviewForCell(void* handle, int x, int y, int z, int side)`
- `Chess3D_GetLegalActionPreviewCount(void* handle)`
- `Chess3D_GetLegalActionPreviewEntry(void* handle, int previewIndex, Chess3DLegalActionPreviewEntryDto* entry)`
- `Chess3D_GetPreviewEntryReason(void* handle, int previewIndex, char* buffer, int capacity)`

The C# wrapper exposes the same flow in `src/ChessApp/NativeChess3DEngine.cs`:

- `BuildLegalActionPreviewForCell(int x, int y, int z, int side)`
- `GetLegalActionPreview()`
- `GetPreviewEntryReason(int previewIndex)`

`Chess3DLegalActionPreviewEntryDto` currently contains:

- `Kind`
- `FromX`, `FromY`, `FromZ`
- `ToX`, `ToY`, `ToZ`
- `Flags`
- `PieceCode`
- `CapturedPieceCode`
- `Side`
- `ReasonCode`

This is the best source of truth for source-cell target highlighting because it is generated by the same native rules authority that later accepts or rejects `TryMakeMove` and related actions.

## Existing AI Candidate API

The server already uses AI/smoke candidates in `OnlineGameSession.FirstAiCandidateCommand`:

- `_engine.BuildAiActionCandidates()`
- `_engine.GetAiActionCandidates()`

The candidate kind mapping is:

- `1` -> `OnlineActionKinds.NormalMove`
- `2` -> `OnlineActionKinds.RubikLayerTurn`
- `3` -> `OnlineActionKinds.ReserveRestore`
- `5` -> `OnlineActionKinds.HodgeProjectedMove`

That API is useful for safe smoke actions and test helpers, but it is not the right UX source for “I clicked this cell; what can this piece do?” because it is broad, scored, and not shaped around the selected source cell. It can remain the safe-action helper while online legal preview uses the existing cell preview ABI.

## Current Online Action Application

`OnlineGameSession.TryApply` currently dispatches:

- `NormalMove` -> `_engine.TryMakeMove(...)`
- `HodgeProjectedMove` -> `_engine.TryMakeProjectedMove(...)`
- `RubikLayerTurn` -> `_engine.RotateLayer(...)`
- `ReserveRestore` -> `_engine.RestoreReservePiece(...)`

`OnlineRoomRegistry.SubmitAction` owns the online authority checks:

- table exists;
- player is seated;
- state hash is current;
- actor matches current seat/side;
- native session accepts or rejects the action.

Any online preview contract must keep this authority model. Preview is a read-only convenience, not permission to bypass `SubmitAction`.

## Minimal Append-Only Protocol Contract

Add new protocol message types later, append-only:

- request: `RequestLegalPreview`
- response: `LegalPreviewResult`

Add a nullable payload to `OnlineProtocolMessage`, for example:

- `OnlineLegalPreviewRequest? LegalPreviewRequest`
- `OnlineLegalPreviewResult? LegalPreview`

Suggested request fields:

- `ExpectedStateHash`
- `SourceX`, `SourceY`, `SourceZ`
- `ActorSide`
- `MacroPlayer`
- `ActionKindFilter`

Suggested result fields:

- `RulesetId`
- `StateHash`
- `ServerSeq`
- `SourceX`, `SourceY`, `SourceZ`
- `ActorSide`
- `MacroPlayer`
- `IsStale`
- `NoLegalActionReason`
- `Options`

Suggested option fields:

- `ActionKind`
- `ActorSide`
- `MacroPlayer`
- `FromX`, `FromY`, `FromZ`
- `ToX`, `ToY`, `ToZ`
- `PromotionType`
- `Side`, `PieceType`, `X`, `Y`, `Z` for reserve restore shape compatibility
- `PrimarySide`
- `Axis`, `Layer`, `QuarterTurns`
- `Flags`
- `PieceCode`
- `CapturedPieceCode`
- `ReasonCode`
- `ReasonText`
- `DisplayText`
- `IsCapture`
- `IsSpecial`
- `IsRecommendedSafeTestAction`

The result should be safe to render directly in the WPF online board:

- normal targets can be highlighted;
- captures can be highlighted differently;
- rejected/blocked options can be listed as reasons if the engine exposes them;
- unsupported special actions can be shown in a mode panel instead of pretending to be normal board clicks.

## Hub Boundary

Add a hub method later:

```csharp
public async Task<OnlineProtocolMessage> RequestLegalPreview(OnlineProtocolMessage message)
```

The hub should:

1. Validate the protocol envelope.
2. Validate auth.
3. Validate room/table/seat.
4. Validate that the caller is allowed to view that table.
5. Call the registry/session preview method.
6. Return `LegalPreviewResult` to the caller only.

Preview should not broadcast to the table because it is a local UI helper. Accepted actions remain the only gameplay mutation broadcast.

## No-Mutation Requirement

Requesting legal preview must not mutate:

- board;
- core stacks;
- fusion state;
- reserve;
- game phase/outcome;
- action history;
- server sequence;
- replay cursor;
- state hash.

The response can include the current `ServerSeq` and `StateHash` for stale-client detection, but it must not advance authoritative state.

## Profile Coverage

Classic Six-Side:

- source-cell preview should return legal self-check-safe normal moves and captures.

Single-Side Training:

- source-cell preview should return training legal moves according to the profile contract.

Asgard / Meru:

- source-cell preview can expose normal/core/capture flags already represented by native preview entries.
- reserve restore remains a dedicated mode action unless or until the native preview entry is sufficient for board highlighting.

Rubik Convergence:

- source-cell preview is not enough for layer turns.
- layer turns should remain a mode panel action and can later be represented by a profile-level legal action preview.

Hodge Projection Duel:

- source-cell preview should not fake a normal move when the required action is a projected composite move.
- Hodge preview should map to `HodgeProjectedMove` options when the native preview exposes `ProjectionComposite`, or remain in the existing Hodge panel until the contract is implemented.

## Security And Logging

Legal preview payloads may contain:

- room/table ids;
- coordinates;
- action kind;
- state hash;
- reason strings.

They must not contain:

- access tokens;
- refresh tokens;
- user passwords;
- private keys;
- runtime keyrings or stores.

The public HTTP 80 server remains diagnostic/dev only. Real credentials must not be used until TLS/domain planning is completed in a separate stage.

## Compatibility

This can be added without breaking existing clients:

- new message types are append-only;
- new nullable DTO fields are append-only;
- existing `SubmitAction`, `RequestSnapshot`, `RequestActionLog`, and matchmaking methods remain unchanged;
- existing smoke tooling can continue using safe AI candidates until the UI consumes the new preview.

## Recommended Implementation Order

1. Add DTOs and JSON source generation entries.
2. Add `OnlineGameSession.BuildLegalPreview(...)` that wraps `NativeChess3DEngine.BuildLegalActionPreviewForCell`.
3. Add `OnlineRoomRegistry.RequestLegalPreview(...)` with no-mutation tests.
4. Add `Chess3DRelayHub.RequestLegalPreview(...)`.
5. Add `ChessOnlineRelayClient.RequestLegalPreviewAsync(...)`.
6. Wire `ChessOnlineApp` source-cell click to request preview.
7. Highlight returned options on the board.
8. Dispatch exact selected preview option through `SubmitAction`.
